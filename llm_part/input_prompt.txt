These events are commands that the supervisor may enable or disable:

UNCONTROLLABLE EVENTS
These events are observations or external occurrences that the supervisor cannot disable:

- blue_not_visible: the blue target is currently not visible.

- blue_visible: the blue target is currently visible.
- green_not_visible: the green target is currently not visible.
- green_reached: the robot has reached the green target.

MANDATORY SCT RULES

1. Do NOT introduce any new controllable or uncontrollable events. Use ONLY the event names listed above, with exactly the same spelling and case.
2. Do NOT invent sensor events beyond the uncontrollable list. Events such as battery_low, target_lost, timeout, failure, or emergency_stop are forbidden because they are not in the baseline alphabet.
3. The provided event lists define the allowed global alphabet. An automaton does NOT have to use every event. Give each plant or specification only the minimal subset relevant to the component or rule it models. Using an event merely because it appears in the allowed list is incorrect.
4. The automaton must be deterministic. For every (state, event) pair, define exactly one next state. Never repeat a (state, event) pair, even when the repeated transition has the same target.
5. Every transition label must be exactly one event from the lists above.
6. For every specification, identify its local uncontrollable-event alphabet from the uncontrollable events used anywhere in that specification. Every state in that specification must have exactly one outgoing transition for each event in that local uncontrollable alphabet.
7. If a locally included uncontrollable event does not affect a specification state, add a self-loop for that event. Do not add unrelated uncontrollable events merely for completeness.
8. A state may enable zero, one, or multiple controllable events. Include every controllable action that is semantically valid in that state; the SCT runtime may select among multiple enabled controllable actions.
9. Determinism still applies when multiple controllable events are enabled: each distinct (state, controllable event) pair must have exactly one target state. Do not repeat the same event from the same state.
10. Do not add controllable self-loops merely to make the automaton appear complete. Add a controllable transition only when that command is semantically valid in the source state.
11. Every state listed in states must be reachable from initial_state. Do not create unused or unreachable states.
12. Use short, descriptive, unique state names containing only letters, numbers, and underscores.
13. Provide exactly one initial state, and ensure initial_state appears in states.
14. Every name in marked_states must appear in states. Prefer marking all states unless the control objective defines a meaningful incomplete or blocking condition.
15. Design a nonblocking specification whenever the control objective permits it: every reachable state should be marked or should have a path to a marked state.
16. Every automaton must have a type field whose value is exactly plant or specification.
17. Every name must be short and contain only letters, numbers, and underscores. Specification names must end with _specification. Plant names must not contain spec or specification.
18. Generate at least one plant or specification, but generate as many separate automata as the control objective genuinely requires. Every generated automaton must have a unique name.
19. Every event used by a generated specification must belong to at least one plant automaton participating in the system. The existing obstacle-avoidance plants already provide full_rotate, move_forward, obstacle_front, obstacle_left, obstacle_right, path_clear, rotate_clockwise, and rotate_counterclockwise. If a specification uses any other event, generate at least one plant containing that event. Across the existing and generated plants, the plant-event union must cover the complete event alphabet of every generated specification.

Do not represent transitions as objects, dictionaries, maps, nested arrays, tuples, or lists of objects.
