WHAT TO OUTPUT

Output one control specification that enforces the control objective. Read `fixed_synthesis_roles`: `G_plants` identifies the plants that define what the robots can do (i.e., the free behavior models) - they are automatically combined into a single generator G; `K_fixed_specifications` identifies the fixed specifications. All specifications are then combined and fused with G to create an overall generator (K) from which the resulting robot controller (i.e. the supervisor) is derived.

Use the given events to fulfill the objective. In particular, use the supplied motion, sensing, and other events (provided as part of the G_plants) to create a specification (e.g., a generator) that realizes the desired control objective for the respective mission.

EVENT MEANINGS

The pipeline appends meanings only for the events available to the current request.

The robot is a rover that operates in a bounded arena. It has a front-facing camera with an 87-degree field of view. The camera determines if sensing events have occurred that relate to the robot's visual perception (e.g., detection of obstacles, colors, and objects).

OUTPUT FORMAT

Return only one small valid JSON object with exactly one top-level field named `automata` which defines the control specification, that is, its 'name',  'initial_state', 'marked_states', and 'transitions'. Do not return Markdown, commentary, explanations, or text outside the JSON.

`automata` must be a non-empty array. Every element must contain exactly these fields:

- `name`: a unique identifier ending in `_specification`
- `initial_state`: the initial state name
- `marked_states`: an array of acceptable marked-state names
- `transitions`: a non-empty array of `[source_state, event, target_state]` arrays

The code derives the automaton type (in this case, a control specification), complete state list, local event alphabet, XML identifiers, and layout. Every state named in `initial_state` or `marked_states` must occur in at least one transition.

Example transition: `["searching", "move_forward", "searching"]`. Do not encode transitions as strings or objects.

SCT RULES

1. Use only events declared by the supplied plants (in G_plants), with exact spelling and case. Select only events relevant to the user input.
2. Every event used by a generated specification must exist in at least one supplied plant. Do not create a plant to introduce a new event.
3. The code derives each specification's local event alphabet from its transitions. Keep transitions amongst states minimal and relevant to the objective.
4. Explicitly define a transition for every uncontrollable event that should change a given state (e.g., if the robot observes something that should trigger a different action). If no transition is defined, a self-loop for this uncontrollable event is automatically added to the state. 
5. Make every automaton deterministic in the sense that each `(state, event)` pair has at most one target.
6. Add controllable event transitions to the states where this makes sense for the control objective.
7. At run-time, zero, one, or multiple controllable events may be enabled in the given state (i.e., they were deemed not to violate the specifications). Where multiple controllable events are enabled, one of them will be picked at random.
8. Every state must be reachable from the initial state (`initial_state`).
9. Use short, unique names containing only letters, numbers, and underscores.
10. Use `marked_states` to define the states that are marked for the control specification. At least one state must be marked. Mark only states that represent stable checkpoints or legitimately repeatable mission conditions. Do not mark transient states with outstanding obligations. However, every state must be marked or have a path to a marked state.

USER INPUT
Search for objects. Once an object has been detected, approach it, and, once it has been reached, pick it up and search for a suitable drop-off zone which could be the red zone, the blue zone, or both. Once a suitable zone has been detected, approach it. Once it has been reached, drop the object and broadcast a message to the other robots that indicates the zone at which the object was dropped. Following delivery, resume with search to repeat the process indefinitely. At all times, take the broadcast messages received from other robots into account to keep track of the difference in the number of objects delivered to the red and blue zones. Choose which zones to deliver to, such that the number of objects delivered to either zone always has a difference of -1 (i.e., the blue zone received one delivery more than the red zone), 0 (i.e., both zones received an equal amount of deliveries), or 1 (i.e., the red zone received one delivery more than the blue zone).
